# v0.10.1 — XLSX color compatibility and per-file diagnostics

A synthetic workbook with `rgb="#9EB3C9"` reproduces openpyxl 3.1.5's
`Colors must be aRGB hex values` failure. On 2026-10-19, PyPI still lists 3.1.5 as latest;
its installed source rejects the leading hash. The online changelog request was blocked by the
network proxy. The originating export tool and Excel/LibreOffice behavior were not verified.
No dependency bump, parser replacement, global monkey-patch or schema migration is introduced.

## Compatibility repair

Only the exact color ValueError in the exception chain permits a single retry. In SpreadsheetML
main-namespace elements of `xl/styles.xml`, literal `rgb="#RRGGBB"` or `rgb="#AARRGGBB"`
loses only `#`; letter case and six/eight-digit length remain unchanged. openpyxl supplies its
normal `00` alpha for six-digit colors. Every other byte of the styles XML is preserved.
Other archive member payloads, names, order and compression methods are retained. openpyxl 3.1.5
reads the literal styles path, ignoring the styles relationship; the fallback follows that behavior.

The repaired ZIP exists only in a mode-0700 temporary directory under the service cache and is
removed on success or failure. Original local files and raw Drive cache bytes are never rewritten.
All styles remain present, including date/time/number formats. Sheet order, text, cell locators,
spans, cached formula values and empty-cell behavior match an equivalent valid workbook.
No formula, macro, external link, network or embedding evaluation is added to extraction.

Successful repair adds document metadata:

```json
{"compatibility_repairs": [{"kind": "xlsx_rgb_hash_prefix", "part": "xl/styles.xml", "count": 1}]}
```

Metadata and search results expose this marker; operator sync warnings identify only the file and
repair kind. It describes a compatibility workaround, not a standards-compliant source file.
Unsupported colors (short forms, named colors, non-hex or seven-digit values) fail the whole repair.
Nonliteral/encoded hashes and non-ASCII-compatible XML encodings are not repaired. A mixed valid
repair and unsupported color is refused without any partial repair.

## Limits and diagnostics

Before openpyxl reads the original, archive preflight enforces at most 10,000 members, 16 MiB
uncompressed styles, 512 MiB total uncompressed payload and a maximum 200:1 compression ratio
per member. These limits also apply to otherwise valid workbooks. Duplicate member names and
missing declared worksheet parts are refused to prevent ambiguous or partial extraction.
Styles containing DOCTYPE or ENTITY declarations are rejected before XML parsing. The patched
XML is parsed and compared against the original tree with only the approved attribute changes.
Other members are streamed during copying, never extracted to source-derived filesystem paths.

Fixed, content-free `ExtractionError` messages have codes:

| Code | Meaning |
| --- | --- |
| `xlsx_unsupported_color` | An RGB value is outside the supported forms. |
| `xlsx_stylesheet_unreadable` | Unsafe/unreadable stylesheet or failed compatibility retry. |
| `xlsx_archive_limit` | ZIP/style resource limit exceeded. |
| `xlsx_parse_failed` | Other loading/iteration error, ambiguous ZIP or missing worksheet. |

Operator per-file errors use `file '<id-or-relative-path>': stage=parse error=ExtractionError
code=xlsx_unsupported_color`. Stages are `download_export`, `parse`, or `index`. Drive coverage
retains `reason` (exception type) and adds `code` alongside `stage`. Causes remain chained for
local debugging but are never copied into reports. Embedding failures remain separate
`embedding:` warnings; provider exception text is omitted. Reader coverage continues redacting
file names and detailed reasons/codes. No capability is added to reader or reviewer profiles.

## Upgrade and rollback

Stop the operator-managed indexer/watcher and disconnect MCP clients for the selected home.
Back up the **entire data home**, including SQLite/WAL state, extracted/effective artifacts,
revisions, configuration and protected credentials. Keep the backup private. Source folders and
Drive remain authoritative and are not changed by this release.

Install the verified `phamviet_local_rag_mcp-0.10.1-py3-none-any.whl` in the intended isolated
environment. Do not install the unrelated PyPI project named `local-rag-mcp`. Verify the wheel
against `SHA256SUMS` from this repository's GitHub Release. Refresh bundled skills with
`install-skills --replace`, retaining any operator-selected skills destination.

- **0.9.0 → 0.10.1:** first startup applies migrations 5–7 inherited from v0.10.0: Vietnamese
  FTS rebuild, float32 vector BLOB copy/cache revision, and monotonic document IDs. These use
  stored data, make no embedding or Drive calls, and preserve existing IDs, chunks, hashes,
  corrections, metadata, relationships and vector JSON. Source re-registration or full reindex
  is unnecessary.
- **0.10.0 → 0.10.1:** no new database migration. Existing indexed content and vectors remain
  intact; retry only files that failed extraction.

Run `local-rag-mcp --home /absolute/data/home doctor --json`, `status`, and `source list`.
Compare document/chunk/vector counts to the backup before retrying files. Reconnect the reader
client and test search/read and coverage. Missing optional OCR/embeddings is a supported degraded
state, distinct from source failures. Resume the watcher only after verification.

To roll back, stop all clients/writers, restore the complete pre-upgrade data-home backup and
reinstall the previous verified wheel (0.9.0 or 0.10.0). Never run 0.9.0 against a database migrated
to schema 7, and never reverse migrations by deleting schema records. Keep post-upgrade source
changes; reconcile after restoring the old derived state.

## Validation

Synthetic fixtures cover valid/invalid RGB forms, number/date/time formatting, three ordered
sheets, cached/uncached formulas, source immutability, byte-preserving copying, cleanup on failure,
XML declarations, archive limits, unrelated errors, Drive/local diagnostics, metadata visibility,
reader redaction and retry behavior. The existing populated-0.9.0 migration regression remains.
The release is gated on the repository CI matrix and clean installed-wheel MCP/skill checks.

Pre-push Linux validation: **130 tests passed** on each of Python 3.11.17, 3.12 and 3.13.5
with the optional NumPy scorer installed; Ruff format/check, strict mypy (28 source files) and
compileall passed. The 26 new XLSX cases use only generated fixtures and blocked external I/O.
Clean-wheel MCP checks passed modern 2026-07-28 and legacy 2025-11-25 protocols; both packaged
skills passed the Codex skill-creator validator. `scripts/verify_xlsx_upgrade.py` exercised the
published 0.9.0 wheel and the new wheel against the same synthetic home through CLI commands:
three existing documents/chunks/vectors were preserved through migrations 5–7; targeted XLSX
retry added one document/vector with no unrelated re-embedding and unchanged source bytes/mtime.
The script uses a loopback-only embedding stub. Drive retry/reporting checks use a fake backend;
no live Drive or production-host recovery has been performed.
